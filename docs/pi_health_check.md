# 라즈베리파이 상태 진단 (아두이노 USB + 12 V 연결 상황)

프로그램: `scripts/pi_health_check.py` (Python 3 표준 라이브러리만 사용)

> **검증 상태 (2026-10-10)**: Windows의 WSL Ubuntu 24.04에서 실행 흐름, 저장, 측정 불가 시 "확인 불가" 처리만 확인했다.
> 커널 로그 분류와 판정 로직은 가짜 로그로 확인했다.
> 카메라 확인(9장, 2026-10-28 추가)도 같은 방식으로 확인했다. WSL에는 카메라가 없어서 "센서 없음·도구 없음" 경로만 실제로 돌았고,
> 정상·고장 판정은 가짜 데이터로만 확인했다.
> **실제 라즈베리파이·아두이노에서는 아직 실행하지 않았다.** Pi에서 처음 실행한 결과를 보고 이 줄을 고친다.

## 0. 이 프로그램이 하는 일과 하지 않는 일

| 한다 (읽기만) | 하지 않는다 |
|---|---|
| Pi 모델, OS, 커널, 부팅 후 경과 시간 읽기 | 시리얼 포트 열기, DTR/RTS 변경 (포트를 열기만 해도 아두이노가 리셋될 수 있음) |
| `vcgencmd measure_temp`, `get_throttled`, `measure_volts core` | GPIO 출력, USB 전원 제어, 재부팅 |
| (Pi 5) `vcgencmd pmic_read_adc EXT5V_V`, `rpi_volt` 저전압 알람 | 부하·스트레스 시험 |
| sysfs의 USB 장치 목록과 그 변화 (`/sys/bus/usb/devices`) | 패키지 설치, 그룹 추가 같은 시스템 설정 변경 |
| `journalctl -k -b` (안 되면 `dmesg`)에서 저전압·과전류·연결 해제·reset·인식 오류 찾기 | 아두이노 펌웨어나 저장소의 다른 코드 변경 |

- 외부 명령마다 timeout(기본 5초)을 둔다. Ctrl+C로 언제든 멈출 수 있고, 멈추면 그때까지의 결과를 정리해서 저장한다.
- 부하를 줄이려고 커널 로그는 표본 간격(2초)과 따로 10초마다 읽는다.
- 이 프로그램은 대회 임무 코드가 아니다. 경기 중에는 실행하지 않는다. Remote SSH는 Wi-Fi를 쓰므로 임무 시작 후 외부 통신 금지(규정 1.3)에 걸린다.

## 1. 먼저 확인할 정보 (사람이 확인)

프로그램이 자동으로 알 수 있는 것은 **Pi 모델뿐**이다 (`/proc/device-tree/model`). 나머지는 직접 확인해서 옵션으로 넣는다.
옵션을 넣지 않으면 결과에 "미확인"으로 기록한다.

| 확인할 것 | 확인 방법 | 옵션 |
|---|---|---|
| 아두이노 정확한 모델 | 보드 인쇄(예: "MEGA 2560 R3"), 구매 기록 | `--arduino-model` |
| 정품 / 호환 | 보드 인쇄·로고, USB 칩 종류(ATmega16U2 또는 CH340 등)를 **실물로** 확인, 구매처 | `--arduino-origin` |
| Pi 모델 | 자동 (`cat /proc/device-tree/model`과 같음) | — |
| Pi 전원 공급 방식 | USB-C 어댑터(정격 몇 V/A, PD 지원 여부)인지, GPIO 5 V 핀으로 넣는지, 무엇에서 오는지 | `--pi-power` |
| 12 V 마이너스(−)가 연결된 곳 | 아두이노 GND 핀·DC 잭만인지, Pi GND나 다른 보드 GND와도 묶였는지 | `--ground-12v` |
| USB 외 추가 연결 | 아두이노와 Pi 사이 GPIO·5 V·GND 선이 있는지 | `--extra-wiring` |

참고: 저장소 문서(`docs/hardware_reference.md` 9·10장)는 Pi 5 + Arduino Mega 2560 R3를 계획으로 적고 있고, Pi 전원 방법은 "미정"이다.
**계획 문서는 실물 확인이 아니다.** 지금 꽂혀 있는 보드를 직접 보고 넣는다.

USB 장치 ID(VID:PID)에 대해:
- `2341`은 Arduino 회사가 등록한 번호지만 호환보드가 같은 번호를 쓰기도 한다. `1a86`은 CH340 계열 USB-시리얼 칩 회사 번호다.
- **USB ID는 USB 칩 정보일 뿐이다. 보드 모델, 정품 여부, 전원 회로(VIN과 USB 5 V를 어떻게 나누는지)를 알려 주지 않는다.** 프로그램도 판정하지 않는다.
- 이 로봇에서는 RRC Lite, RPLIDAR도 USB 시리얼 장치다. 목록에 시리얼 장치가 있다고 그것이 아두이노라는 뜻은 아니다.

## 2. 실행 환경

프로그램은 **라즈베리파이의 Linux에서** 실행한다. Windows에서 실행하면 안내만 출력하고 끝난다.

### Windows의 VS Code에서 Remote SSH로 Pi에서 실행하기
1. Pi에서 SSH가 켜져 있는지 확인: Pi 터미널에서 `systemctl status ssh` (꺼져 있으면 팀이 판단해서 직접 켠다. 프로그램은 설정을 바꾸지 않는다).
2. Pi 주소 확인: Pi에서 `hostname -I`.
3. Windows VS Code → 확장(Extensions)에서 **Remote - SSH** 설치.
4. `F1` → `Remote-SSH: Connect to Host...` → `사용자이름@Pi주소` 입력 → 비밀번호 입력.
5. 접속되면 `File → Open Folder`로 Pi에 있는 저장소 폴더(예: `~/polly`)를 연다.
6. VS Code 아래쪽 터미널(`` Ctrl+` ``)은 이제 **Pi의 터미널**이다. 여기서 3장의 명령을 실행한다.
   왼쪽 아래 초록 표시가 `SSH: Pi주소`인지 확인한다. (Windows 터미널에서 실행하면 Pi가 아니라 PC를 검사하게 된다.)

저장소가 Pi에 없으면 Pi에서 `git pull` 하거나 `scp scripts/pi_health_check.py 사용자@Pi주소:~/`로 이 파일만 복사해도 된다.

## 3. 실행 명령

```bash
cd ~/polly

# 기본: 120초 동안 2초 간격, 결과를 현재 폴더에 CSV + JSON으로 저장
python3 scripts/pi_health_check.py

# 확인한 정보를 같이 기록 (예시 값. 실제 확인한 내용으로 바꿔 넣는다)
python3 scripts/pi_health_check.py \
  --arduino-model "Mega 2560 R3" --arduino-origin "호환 (CH340)" \
  --pi-power "USB-C 5V 5A 어댑터" --ground-12v "아두이노 GND 핀만" --extra-wiring "없음" \
  --output-dir ~/diag

# 시간·간격 바꾸기, 저장 형식 고르기
python3 scripts/pi_health_check.py --duration 300 --interval 5 --format json

# 아두이노를 분리한 기준 측정 (5장 1단계)
python3 scripts/pi_health_check.py --baseline --output-dir ~/diag
```

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--duration` | 120 | 관찰 시간 [초] |
| `--interval` | 2 | 표본 간격 [초] (0.5 이상) |
| `--log-interval` | 10 | 커널 로그 다시 읽는 간격 [초] |
| `--cmd-timeout` | 5 | 외부 명령 하나의 제한 시간 [초] |
| `--format` | both | `csv`, `json`, `both` |
| `--output-dir` | `.` | 저장 폴더 (없으면 만든다) |
| `--baseline` | 꺼짐 | 아두이노 분리 상태 기준 측정이라고 표시 |

### 권한 때문에 "확인 불가"가 나올 때
- `vcgencmd`가 권한 부족이면 보통 `video` 그룹이 필요하다. 커널 로그가 권한 부족이면 `adm`(또는 `systemd-journal`) 그룹이 필요하다.
  Ubuntu는 일반 사용자의 `dmesg`를 막아 둔다.
- 그룹 추가는 시스템 설정 변경이므로 프로그램이 하지 않는다. 필요하면 팀이 판단해서 직접 한다.
  한 번만 보려면 `sudo python3 scripts/pi_health_check.py`로 실행해도 된다 (읽기만 하는 것은 같다).
- `vcgencmd`가 없으면(Ubuntu에서 패키지가 없는 경우) 온도는 커널 온도 센서(`/sys/class/thermal`)로 대신 읽고, throttled 값은 "확인 불가"가 된다.

## 4. 결과 읽는 법

각 항목은 세 가지 중 하나로 나온다.
- **관찰된 이상 없음**: 이번 관찰 동안 그 항목에서 기준을 넘은 기록이 없었다. 하드웨어가 멀쩡하다는 뜻은 아니다.
- **이상 관찰**: 기준을 넘은 값이나 관련 로그가 있었다. 근거에 값과 로그 줄이 나온다.
- **확인 불가**: 명령 없음, 권한 부족, 센서 없음, 시간 초과, 출력 해석 실패 중 하나다. **측정이 한 번이라도 빠지면 "이상 없음"으로 처리하지 않는다.**

| 항목 | 기준과 주의 |
|---|---|
| CPU 온도 | 80 °C 이상이면 이상 관찰 |
| throttled 현재 (비트 0~3) | 0 저전압, 1 주파수 제한, 2 throttling, 3 온도 제한. 검사 중 한 표본이라도 켜지면 이상 관찰 |
| throttled 이력 (비트 16~19) | 부팅 후 한 번이라도 같은 상태가 있었다는 표시. 재부팅 전까지 남는다. **검사 시작 때 이미 켜져 있던 것과 검사 중 새로 켜진 것을 나눠서 보여 준다.** 시작 때부터 켜져 있으면 과거 기록일 뿐, 언제·왜 생겼는지 알 수 없고 이번 아두이노 연결 탓으로 단정하지 않는다 |
| 코어 전압 (`measure_volts core`) | SoC 내부 코어 전압이다. **USB 5 V나 아두이노 VIN 전압이 아니다.** 판정에 쓰지 않고 기록만 한다 |
| EXT5V_V (Pi 5만) | Pi 5 PMIC가 읽은 Pi 외부 5 V 입력 참고값. 4.75 V 미만이면 이상 관찰. **아두이노 쪽 전압이 아니며, USB 역류 여부도 이것으로 판단할 수 없다** |
| rpi_volt 저전압 알람 (Pi 5) | 커널 hwmon `in0_lcrit_alarm`. 1이면 이상 관찰. 없으면 확인 불가 |
| USB 장치 연결 변화 | 검사 중 장치 추가·제거·재연결(장치 번호 변경)이 있으면 이상 관찰. 그 사이 손으로 꽂거나 뺐다면 그 때문일 수 있다 |
| USB 시리얼 장치 인식 | 연결 상태 검사인데 시리얼 장치가 하나도 없으면 이상 관찰. 있으면 목록과 USB 칩 정보만 보여 준다 |
| 커널 로그 이력 (검사 전) | 부팅 후 검사 시작 전의 저전압, USB 과전류, 인식 오류(`error -71` 등), 같은 장치 reset 3회 이상. 과거 기록이며 원인은 따로 확인해야 한다 |
| 커널 로그 새 기록 (검사 중) | 검사 중 저전압·과전류·연결 해제·reset·인식 오류·새 장치 인식이 하나라도 있으면 이상 관찰 |

`get_throttled`가 `0x0`이어도 "손상 없음"이나 "전기적으로 안전"이라는 뜻이 아니다.
Pi 펌웨어가 감지하는 전압 저하·온도 제한이 없었다는 뜻일 뿐이다. 역류, 접지 문제, 부품 손상은 이 값으로 알 수 없다.

### 결과 해석 예시 (실제 측정이 아니라 설명용으로 만든 출력)

```
[14:02:10] 온도 52.3°C | throttled 0x50000 (현재 비트 없음) | 코어 0.8700V | EXT5V 5.081V | USB 3개
...
=== 결과 요약 ===
[관찰된 이상 없음] CPU 온도
    근거: 61회 측정, 51.8~53.9°C (기준 80°C 미만, 출처 vcgencmd)
[관찰된 이상 없음] throttled 현재 상태 (비트 0~3, 검사 중)
    근거: 61회 표본 모두 0. 표본 사이 짧은 순간은 놓칠 수 있어 이력 비트를 함께 본다
[이상 관찰] throttled 이력 (비트 16~19, 검사 시작 전부터)
    근거: 시작 시점 값 0x50000: 저전압 발생 이력, throttling 발생 이력. 부팅 후 언제·무엇 때문에 ...
[관찰된 이상 없음] throttled 이력 (검사 중 새로 기록)
    근거: 시작 0x50000 → 끝 0x50000, 새로 켜진 이력 비트 없음 ...
[확인 불가] 커널 로그 이력 (부팅 후 검사 시작 전)
    근거: journalctl: 권한 부족 ... / dmesg: 권한 부족 ... → 커널 로그를 읽지 못함
```

이 예시는 이렇게 읽는다.
- 부팅 후 어느 시점에 저전압이 있었다 (`0x50000`). 그런데 검사 2분 동안은 새로 생기지 않았다.
- 과거 저전압이 아두이노 연결 때문인지, 부팅할 때 전원 어댑터 때문인지, 다른 USB 장치 때문인지는 **이 결과로 알 수 없다.**
  다음 단계: 재부팅해서 이력을 지운 뒤 5장 순서대로 다시 기록하고, 권한을 갖춰서(`sudo`) 커널 로그 시각을 확인한다.
- 커널 로그를 못 읽었으므로 "로그상 이상 없음"이라고 말할 수 없다.

## 5. 비교 검사 순서

한 번에 한 조건만 바꾸고, 단계마다 결과 파일을 남긴다. 비교가 쉽도록 각 단계 전에 Pi를 재부팅해서 throttled 이력을 지운다.

1. **기준 기록 (아두이노 분리)**: 아두이노 USB를 빼고 12 V도 끈다. Pi만 켠 채 `--baseline`으로 실행한다.
   여기서 이미 저전압·과전류가 나오면 Pi 자체 전원부터 확인한다 (아두이노와 관계없음).
2. **USB만 연결 (12 V 끔)**: 아두이노는 USB 전원만 받는다. 실행해서 1단계와 비교한다.
3. **12 V와 USB 동시 연결 재시험**: **아래 조건을 모두 확인하기 전에는 하지 않는다.**
   - 지금 쓰는 아두이노 보드의 정확한 모델과 그 보드의 회로도(VIN과 USB 5 V 자동 선택 회로가 있는지, 어떤 부품인지)를 확인했다.
     정품 Mega 2560 R3는 그런 선택 회로가 있다고 알려져 있지만, **호환보드는 다를 수 있으니 실제 보드로 확인한다.**
   - 12 V 전원의 극성과 전압, 마이너스 연결 위치, USB 외 추가 배선을 확인했다 (1장).
   - 6장의 멀티미터 실측(특히 "Pi에 꽂지 않은 상태에서 USB 케이블 VBUS 전압")을 끝냈고, 역류 경로가 보이지 않았다.
   조건이 갖춰지면 2단계와 같은 방법으로 실행해서 1·2단계와 비교한다.

세 단계 결과를 비교할 때도, 차이가 나면 "그 조건에서 이런 기록이 관찰됐다"까지만 말한다. 원인 확정은 실측으로 한다.

## 6. 소프트웨어 검사와 전기 실측 구분

| 소프트웨어로 볼 수 있는 것 (이 프로그램) | 멀티미터 등으로 실측해야 하는 것 |
|---|---|
| Pi 펌웨어가 감지한 저전압·제한 상태 (`get_throttled`) | 12 V 전원의 실제 전압과 극성 (VIN–GND) |
| Pi 5 외부 5 V 입력 참고값 (EXT5V_V) | 아두이노 5 V 핀 전압: 12 V만 연결했을 때, USB만 연결했을 때 |
| USB 장치 인식·연결 해제·reset·과전류 로그 | **USB 역류 확인**: 아두이노에 12 V만 넣고 USB 케이블은 아두이노에만 꽂은 채, **Pi에 꽂지 않은 쪽 플러그의 VBUS–GND 전압** (USB 브레이크아웃 보드나 USB 테스터 사용). 전압이 나오면 역류 경로가 있는 것이므로 Pi에 꽂지 않는다 |
| SoC 온도 | 전원을 모두 끈 상태에서 12 V 마이너스, 아두이노 GND, Pi GND 사이 도통(어디가 묶였는지) |
| | Pi 전원 입력 단자의 실제 전압 (USB-C 또는 GPIO 5 V 핀) |
| | 보드·레귤레이터·케이블 커넥터 발열 (손을 대지 말고 비접촉 온도계 권장) |

- **역류 확인에 라즈베리파이를 시험 부하로 쓰지 않는다.** 즉 "Pi에 꽂아 보고 켜지는지·로그가 뜨는지"로 역류를 판단하지 않는다.
  역류 여부는 Pi를 빼고 위 방법으로 잰다.
- 이 저장소 계획상 Pi 전원은 GPIO 5 V 핀으로 넣을 수도 있다 (`hardware_reference.md` 9장, 미정).
  GPIO 5 V 핀 입력은 USB-C 입력과 달리 보호 회로를 거치지 않으므로 실측을 더 꼼꼼히 한다.

## 7. 즉시 중단 기준

다음 중 하나라도 있으면 **시험을 이어가지 않는다.** 프로그램 결과와 상관없다.
- 탄 냄새, 연기, 타닥거리는 소리
- 보드·레귤레이터·USB 커넥터·케이블이 손대기 어려울 만큼 뜨거움 (비정상 발열)
- Pi나 아두이노가 저절로 꺼졌다 켜지기를 반복함

조치: 물리 비상정지나 전원 스위치로 **12 V와 Pi 전원을 모두 끊는다** → USB를 뺀다 → 식을 때까지 만지지 않는다 → 팀에 알리고 배선·보드를 점검한 뒤에만 다시 시험한다.
Ctrl+C로 프로그램만 멈추는 것은 전기적 조치가 아니다.

## 8. 저장 파일

- `pi_health_YYYYMMDD_HHMMSS.csv`: 표본마다 한 줄 (시간, 온도, throttled 16진수와 해석, 코어 전압, EXT5V, 알람, USB 개수, 연결 변화, 새 로그).
  Excel에서 한글이 깨지지 않게 BOM을 붙인 UTF-8.
- `pi_health_YYYYMMDD_HHMMSS.json`: 위 내용과 함께 시스템 정보, 사용자 확인 정보, 처음·마지막 USB 장치 목록, 커널 로그 이력과 새 기록, 요약 판정.
- `--baseline`이면 파일 이름 끝에 `_baseline`이 붙는다.
- 결과 파일은 저장소에 커밋하지 않는다 (`--output-dir ~/diag`처럼 저장소 밖에 두기를 권장).

## 9. AI Camera (IMX500) 연결과 확인

카메라: Raspberry Pi AI Camera (Sony IMX500). `docs/hardware_reference.md` 1장 기준으로 리본 케이블을 Pi 5 **CAM0**에 꽂는다.
URDF(`poli_description`)도 CAM0 기준이다. 카메라 탐지 노드 `camera_vision`은 조원 B 담당이라 이 진단은 그 코드를 바꾸지 않는다.

### 순서
1. **꽂기 전 기준 기록**: `python3 scripts/pi_health_check.py --duration 30 --camera absent`
2. **Pi 전원을 완전히 끈다** (`sudo shutdown -h now` 후 전원 분리). CSI 카메라는 전원이 켜진 채로 꽂거나 빼지 않는다.
   정전기를 조심하고, 손은 보드 가장자리만 잡는다.
3. 리본 케이블 연결:
   - Pi 5 카메라 커넥터는 좁은 22핀이다. 카메라 쪽 커넥터와 폭이 다르면 Pi 5용 케이블(22핀↔15핀)을 쓴다.
   - 커넥터의 걸쇠를 살짝 들어 올리고, 케이블을 끝까지 곧게 넣은 뒤 걸쇠를 누른다. **금속 접점 방향은 Pi 5 공식 안내 그림대로 맞춘다.**
     방향이 틀리거나 비스듬히 들어가면 인식되지 않는다.
4. 전원을 켜고 다시 실행한다: `python3 scripts/pi_health_check.py --duration 30`
5. 실제 영상까지 확인: `python3 scripts/pi_health_check.py --duration 10 --camera-capture --output-dir ~/diag`
   → `~/diag/camera_날짜_시간.jpg`를 열어 직접 본다 (VS Code Remote SSH 탐색기에서 열 수 있음).
   **`camera_vision` 노드나 미션 launch가 켜져 있으면 카메라가 사용 중이라 촬영이 실패한다.** 먼저 끈다.

### 카메라 항목 판정
| 항목 | 보는 것 | 이상일 때 먼저 볼 것 |
|---|---|---|
| 카메라 센서 인식 (커널 I2C) | `/sys/bus/i2c/devices/*/name`에 `imx500`이 있고 드라이버가 붙었는지 | 케이블 방향, 끝까지 꽂혔는지, 포트(CAM0/CAM1), `/boot/firmware/config.txt`의 `camera_auto_detect`·`dtoverlay` 줄 |
| 카메라 모델 (imx500 기대) | `rpicam-hello --list-cameras`, Picamera2 목록의 센서 이름 | 다른 카메라가 꽂혀 있지 않은지 |
| Picamera2 사용 가능 | `camera_vision`이 쓰는 라이브러리로 카메라가 보이는지 | 모듈이 없으면 "확인 불가". 설치 여부는 팀(조원 B)이 판단 |
| IMX500 펌웨어 파일 | `/lib/firmware/imx500_loader.fpk`, `imx500_main.fpk`가 있는지 | 없으면 센서가 동작하지 않을 수 있음. 커널 로그에 firmware 오류가 있는지 함께 본다 |
| 카메라 커널 로그 | `imx500`, `rp1-cfe` 줄에 fail·error·timeout이 있는지 | 오류 문구 그대로 팀에 공유 |
| 테스트 사진 | `--camera-capture`일 때만. 640×480 사진 저장, 평균 밝기 | 거의 검정이면 렌즈 덮개·조명. "busy"면 다른 프로그램이 카메라를 쓰는 중 |

- 기본 실행은 카메라 **목록만 읽고 영상은 켜지 않는다.** 사진은 `--camera-capture`를 붙였을 때만 찍는다. 카메라는 바퀴·집게를 움직이지 않는다.
- 사진에 보이는 색으로 빨간 대상 탐지가 맞는지는 이 진단이 판단하지 않는다. 탐지 기준값(`RED_*`, `CAMERA_HFLIP`)은 조원 B가 `camera_vision`에서 실측으로 정한다.
- 대회 규정 Q6: 카메라 보드나 케이블 주변에 빨간 부품·LED가 보이면 가린다 (`docs/competition/rules_compliance.md`).
- 아두이노만 점검할 때처럼 카메라를 볼 필요가 없으면 `--camera skip`.
